ABSTRACT

Machine learning (ML) models operating in live production environments suffer from a critical operational hazard known as silent model degradation. Unlike traditional web services where runtime failures manifest immediately through HTTP 500 errors or application crashes, deployed ML endpoints continue serving HTTP 200 OK responses with low latency even as their predictive accuracy deteriorates due to real-world statistical divergence between incoming production requests and baseline training data (covariate shift or data drift).

This capstone project establishes a production-grade, end-to-end MLOps pipeline for Credit Default Risk Prediction to solve this challenge. The system combines six core engineering pillars: (1) Machine Learning Model Engineering with an optimized HistGradientBoostingClassifier achieving 96.24% accuracy and a 0.9787 ROC-AUC score; (2) Asynchronous REST API serving in FastAPI with Pydantic v2 validation; (3) An autonomous in-memory drift engine executing two-sample Kolmogorov-Smirnov (KS) tests (p < 0.05) and Population Stability Index (PSI) computations (PSI ≥ 0.20); (4) Full OpenMetrics telemetry via Prometheus and Grafana; (5) Multi-stage Docker containerization and local Kubernetes (Kind) deployment with Horizontal Pod Autoscaling (HPA); and (6) A 5-stage GitHub Actions CI/CD automation pipeline (100% passing). The system is deployed live on Vercel with interactive traffic simulation.

Index Terms: Machine Learning Operations (MLOps), Covariate Shift, Data Drift, Kolmogorov-Smirnov Test, Population Stability Index (PSI), Prometheus Telemetry, Kubernetes Autoscaling, FastAPI, Continuous Delivery.

CHAPTER 1: INTRODUCTION & PROBLEM STATEMENT

1.1 The Silent Failure Mode in Machine Learning Systems

In conventional software engineering, component failures are explicit: network disconnections throw socket exceptions, syntax bugs prevent process starts, and deadlocks cause HTTP 504 timeouts. These failures trigger immediate alarms in Site Reliability Engineering (SRE) monitoring consoles.

Conversely, machine learning systems fail silently [1]. A deployed credit risk scoring endpoint continues responding with HTTP 200 OK and sub-10ms latency; yet, the underlying predictions become statistically invalid due to covariate shift (changes in the distribution of input features P(X) between training and production) or concept drift (changes in the relationship between input features and target labels P(y|X)) [2]. Without automated statistical drift monitoring, financial institutions unknowingly issue credit to high-risk applicants, incurring severe financial and regulatory losses.

1.2 Project Objectives

The primary engineering objectives of this project are:

  • Automated Model Engineering: Train a credit default classifier with strict CI/CD gates (ROC-AUC ≥ 0.75).
  • Asynchronous Serving: Serve predictions via FastAPI with sub-millisecond model inference and Pydantic v2 validation.
  • Statistical Drift Engine: Implement Kolmogorov-Smirnov hypothesis testing and Population Stability Index (PSI) without third-party SaaS dependencies.
  • Time-Series Observability: Expose 14 OpenMetrics time-series telemetry streams scraped by Prometheus and displayed on Grafana.
  • Cloud-Native Deployment: Multi-stage Docker containerization and Kubernetes manifests with CPU-driven autoscaling.
  • 5-Stage CI/CD Gating: Enforce linting, 12 passing unit tests, model quality gating, container smoke testing, and Kubernetes dry-runs.

3.2 Histogram-Based Gradient Boosting Algorithm

To enable sub-millisecond CPU inference without external C/C++ runtime dependencies, we implemented Scikit-Learn’s HistGradientBoostingClassifier [4]. The algorithm discretizes continuous features into K = 256 histogram bins, reducing split finding complexity from O(N log N) to O(N × K). The pipeline prepends a StandardScaler to standardize feature magnitudes, trained with hyperparameters: max_iter=150, learning_rate=0.08, and max_depth=6.

In serverless environments, ASGI startup hooks may not trigger before the first incoming request. We implemented lazy singleton loading: if the model object is None at request arrival, the system safely loads artifacts on demand. To prevent memory leaks, requests are held in a circular collections.deque(maxlen=500), restricting buffer memory footprint to < 2 MB.

CHAPTER 5: STATISTICAL DATA DRIFT DETECTION ENGINE

Figure 3: Statistical Drift Detection Pipeline (KS-Test and PSI Engine)

5.1 Two-Sample Kolmogorov-Smirnov (KS) Test Formulation

The Kolmogorov-Smirnov test is a non-parametric test comparing the Empirical Cumulative Distribution Functions (ECDFs) of the reference baseline training dataset Fref(x) and the production sliding window Fcurr(x) [6]:

F(x) = (1 / N) Σ [ I(Xi ≤ x) ]
(2)

The test statistic D is the supremum vertical distance between the two empirical distributions:

D = sup | Fcurr(x) - Fref(x) |
(3)

Under the null hypothesis H0, both samples originate from identical distributions. If the asymptotic two-tailed p-value falls below α = 0.05, H0 is rejected and the feature is flagged as drifted.

5.2 Population Stability Index (PSI) Derivation

While the KS test evaluates statistical significance, the Population Stability Index (PSI) quantifies the geometric magnitude of population shift [7]. The reference dataset is segmented into B = 10 quantile bins bk:

PSI = Σk=1..10 [ (Pcurr,k* - Pref,k*) × ln( Pcurr,k* / Pref,k* ) ]
(4)

where P* = max(P, 10-4) provides zero-frequency smoothing. Table IV outlines the operational interpretation tiers:

Table IV: Standard Population Stability Index (PSI) Interpretation Tiers
PSI Range Classification Distribution State System Action
PSI < 0.10StableNegligible distributional shiftHealthy gauge; continue normal operation
0.10 ≤ PSI < 0.20Moderate ShiftNoticeable population shiftWarning gauge; monitor traffic closely
PSI ≥ 0.20Significant DriftCritical distribution divergenceAlarm gauge; trigger retraining alert

5.3 Dataset-Level Aggregate Alarm Policy

Individual feature drift flags are aggregated into an overall Drift Share:

Drift Share = [ Count of Features with (p < 0.05 OR PSI ≥ 0.20) ] / 8.0
(5)

When Drift Share ≥ 0.30 (3 or more drifted features), the binary alarm gauge ml_dataset_drift_detected is set to 1.0, triggering visual alerts in Grafana and Vercel.

CHAPTER 11: VIVA VOCE DEFENSE GUIDE & EVALUATION Q&A

This section provides authoritative technical answers to the most common defense questions posed by faculty evaluators and examiners:

Q1. What distinguishes MLOps from conventional DevOps?
Response: DevOps manages code and binaries where failures are explicit (crashes, exceptions, HTTP 500 errors). In contrast, ML systems manage code, model parameters, and statistical data distributions. ML models fail silently: the serving endpoint returns HTTP 200 OK responses with low latency while making disastrously inaccurate business decisions because incoming production data has diverged from training data (covariate shift). MLOps bridges this gap with automated data validation, statistical drift telemetry, and automated model governance.

Q2. Why deploy both the Kolmogorov-Smirnov (KS) test and the Population Stability Index (PSI)?
Response: The two-sample KS test is a non-parametric hypothesis test that establishes whether a statistically significant difference exists (p < 0.05). However, on large production samples, trivial shifts can yield p < 0.05. The PSI quantifies the magnitude of shift across 10 quantile bins. Combining both prevents false positive alarms while ensuring that substantial population shifts (PSI ≥ 0.20) reliably flag models for retraining.

Q3. Why select HistGradientBoostingClassifier over traditional XGBoost or deep neural nets?
Response: HistGradientBoosting uses histogram binning (256 discrete bins), reducing split evaluation complexity from O(N log N) to O(N × K). It achieves near-identical accuracy (0.9787 ROC-AUC) without requiring external C/C++ build chains, ensuring instant portability across Linux, Windows, and Vercel serverless runtimes with sub-millisecond CPU inference latency.

Q4. How does the application handle cold-start overhead in serverless cloud environments?
Response: In serverless environments like Vercel, standard ASGI lifespan events do not always trigger before the first incoming request. We implemented lazy singleton loading: if the model pipeline or baseline dataset is None upon request entry, the service transparently reads artifacts/model.joblib and initializes the drift engine before serving the response.

Q5. How is memory bounded in the production rolling buffer?
Response: The sliding window buffer uses a fixed-capacity collections.deque(maxlen=500). When new inference payloads arrive, older samples are automatically evicted in O(1) time. This bounds memory consumption to < 2 MB regardless of whether the service handles thousands or millions of requests.

Q6. Explain the Kubernetes elastic autoscaling policy implemented in this project.
Response: The project configures a Horizontal Pod Autoscaler (HPA) in k8s/ml-hpa.yaml targeting the ml-credit-service deployment. The HPA monitors pod CPU utilization. When average CPU utilization exceeds 70%, the controller dynamically scales replicas from 1 up to a maximum of 5, providing automatic elasticity under traffic spikes.
